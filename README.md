**한국어** · [English](README.en.md)

**주제와 자료를 주면 목차·조사계획부터 제안하고, 확인한 방향에 따라 초안과 근거·검수 기록을 만드는 [Claude Code](https://claude.com/claude-code) 플러그인입니다.**

예를 들어 중소기업 인력정책 보고서를 준비할 때, 메모를 첨부해 목차를 받고 “해외사례를 더 넣어줘”라고 조정할 수 있습니다. 초안 작성 뒤에는 집필과 분리된 검토 역할이 주장·수치·출처를 대조합니다. 결과는 마크다운으로 남으며, 별도 변환 도구를 연결하면 한글 파일(`.hwpx`)로 만들 수 있습니다.

## 30초 소개

[![정책연구 주제·자료가 설계, 조사·집필, 별도 검수와 기록으로 이어지는 흐름](docs/media/intro-preview.gif)](docs/media/intro.mp4)

*Claude Code의 요청·응답과 결과 파일을 재구성한 30초 사용 예시입니다. 가상 과제이며 실제 실행 녹화는 아닙니다.*

## 실제로는 이렇게 씁니다

**예: 지자체의 중소기업 AI 인력정책 보고서를 준비할 때.** 플러그인을 설치한 Claude Code에서 보유한 메모를 지정하고 다음처럼 요청합니다.

```text
지역 중소기업의 AI 인력정책 보고서를 준비해줘.
교육지원과 전문인력 연계를 비교하고 싶어.
@메모.md를 읽고 목차와 조사계획부터 보여줘.
```

1. **목차를 먼저 확인합니다.** 조사·집필 전에 연구 질문과 목차를 제시합니다. “3장에 해외사례를 추가해줘”처럼 방향을 조정한 뒤 진행합니다.
2. **주장에 맞는 근거를 모읍니다.** `_workspace/03_evidence.md`에 사실·출처를 정리하고, 확보하지 못한 자료는 미확보로 남깁니다.
3. **초안을 별도로 검수합니다.** 예를 들어 “교육지원의 효과가 가장 크다”는 문장에 비교 근거가 없으면, `_workspace/05_draft_review.md`에 해당 위치와 문제, 수정 방향을 기록합니다.

**확인할 결과:** `_workspace/04_report_draft.md`의 초안, `03_evidence.md`의 근거, `05_draft_review.md`의 검수 기록입니다. 설계와 집필 전 점검도 `01_research_design.md`·`02_design_review.md`에 남습니다.

**차별점:** 초안을 쓰는 역할과 읽기 전용 검토 역할을 나누고, 본문의 주장과 근거를 대조한 기록을 남깁니다. 사용자는 결과 문장뿐 아니라 무엇을 확인했고 어떤 자료가 부족한지도 볼 수 있습니다.

처음에는 [가상 업무 요청문](examples/intro-request.md)으로 목차 설계부터 확인해 보세요. 위 장면의 과제·검수 문장은 기능을 설명하는 예시이며 실제 정책 효과를 주장하지 않습니다.

## 무엇이 다른가요

보고서에 출처 링크가 붙어 있어도 **그 원문이 본문의 수치를 뒷받침하는지는 별도로 확인해야 합니다.** 이 플러그인은 그 대조를 작업 절차에 포함하고 결과를 기록합니다.

그래서 직접 재봤습니다. 같은 주제를 일반 Claude Code와 이 플러그인에 각각 맡기고, 제3자가 양쪽이 인용한 링크 14개를 **전부 열어서** 원문과 대조했습니다.

| | 일반 Claude Code | 이 플러그인 |
|---|---|---|
| 인용한 자료를 실제로 열어봤나 | 한 번도 안 열어봄 | 중요한 숫자는 전부 확인 |
| 숫자·출처가 틀린 것 | **2건** (모두 단정하는 말투) | **0건** (확인 못 한 건 `[보강 필요]`로 표시) |
| 작업 과정이 파일로 남았나 | 안 남음 | 5개 파일로 남음 |

이 단일 비교에서는 **일반 Claude Code의 문장이 더 매끄럽다고 평가했습니다.** 다만 해당 초안에는 틀린 숫자가 두 개 섞여 있었고, 근거 대조 기록이 남지 않았습니다. 이 결과를 모든 주제나 실행의 성능 차이로 일반화할 수는 없습니다.

## 어떤 순서로 진행되나요

```
목차 설계 → 🚦1차 점검 → ★목차 확인 요청 → 자료 조사 → 본문 집필 → 🚦2차 점검 → 한글 파일
```

중간에 **두 번 멈춰 섭니다.** 첫 번째는 목차가 잘못되지 않았는지 보는 자리입니다. 목차가 어긋난 채로 50쪽을 써 버리면 되돌릴 방법이 없기 때문에, 쓰기 전에 확인합니다. 두 번째는 다 쓴 원고를 검사하는 자리입니다. 완성된 글은 그럴듯해 보여서 스스로 의심하기 어렵기 때문에, **글을 쓰지 않은 다른 AI**가 읽기 전용으로 검사합니다.

실제로 이 점검에서 걸린 것들입니다. 존재하지 않는 출처 3건, 단위를 10배로 잘못 환산한 숫자, 전체 평균을 특정 집단의 값처럼 써 놓은 부분, 그리고 근거가 부족한데 너무 세게 잡은 연구 질문입니다.

## 이렇게 쓰시면 됩니다

평소 말하듯 요청하시면 됩니다.

```
지역 소멸 대응 정책연구보고서 써줘. 메모랑 통계 첨부했어      ← 본문 50쪽 이상
이 주제로 4쪽짜리 정책브리프만 빠르게                        ← 짧은 요약 보고서
이 200쪽 보고서 검수하고 근거 약한 곳 보완해줘               ← 이미 있는 보고서 손보기
3장을 해외사례 중심으로 바꿔줘                               ← 목차 확인 단계에서
```

마지막 줄처럼, 목차를 보여드릴 때 고쳐 달라고 하시면 그 자리에서 다시 짭니다. **방향을 바꾸기에 가장 값싼 시점**입니다.

## 무엇이 남나요

완성된 보고서 하나만 나오는 게 아니라, **작업 과정이 전부 파일로 남습니다.**

목차 설계안, 1차 점검에서 무엇을 왜 지적했는지, 어떤 사실을 어디서 가져왔는지 정리한 목록, 본문 초안, 2차 점검 지적과 실제로 고친 내역, 그리고 최종 한글 파일입니다.

몇 달 뒤에 "이 숫자 어디서 나온 거냐"는 질문을 받았을 때 답할 수 있다는 뜻입니다.

## 알아두실 점

- 한글 파일(`.hwpx`)로 만들려면 [kordoc](https://github.com/chrisryugj/kordoc)이라는 변환 도구가 따로 필요합니다. 없어도 마크다운까지는 정상적으로 나옵니다.
- 표준 보고서는 조사와 검증 때문에 **시간이 꽤 걸립니다.** 급하실 때는 "빨리 해줘"라고 말씀하세요 — 조사를 나눠 동시에 돌리고 반복 점검을 줄이는 쾌속 방식으로 바꿉니다. 실행 중 어느 단계가 예상보다 많이 늦어지면 완료된 중간 결과를 보여드리고 계속 갈지 여쭙니다. 형식 변환처럼 기계적인 단계는 처음부터 가벼운 모델이 맡아 시간을 아낍니다. 다만 **검사하는 AI는 어떤 경우에도 가볍게 바꾸지 않습니다.**
- **점검이 오류를 줄여주긴 하지만 없애주지는 못합니다.** 검사하는 AI도 같은 계열이라 비슷한 착각을 할 수 있습니다. 최종 확인은 사람이 해야 합니다.
- 위 비교 실험은 **한 주제를 한 번 돌려본 것**입니다. 통계적으로 증명된 수치가 아니라, 직접 재현해 보실 수 있는 사례로 봐주세요.
- 국내 정책연구 관행(한글 파일 제출, 국문 자료 중심)에 맞춰져 있습니다.
- [설치·설정에서 막힐 때](docs/runtime-notes.md) · [이런 점검 구조를 직접 만들고 싶다면](docs/verification-gates.md)
