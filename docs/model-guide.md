# 어떤 모델로 돌리나요 · 얼마나 걸리나요 · 일반 Claude Code와 무엇이 다른가요

2026년 10월 10일 정책 브리핑 한 건을 시범으로 돌려 잰 값이다. 주제는 "AI 기본법 시행 뒤 고영향 AI 규율 점검과 하위법령 보완 과제", 분량은 4~6쪽, 독자는 부처 실무자 회의였다. 같은 입력으로 단계별 모델을 바꿔 돌렸고, 결과물은 어느 모델이 썼는지 가린 채 채점했다. **한 주제를 한 번 돌린 결과**라 경향으로 읽어야 한다.

## 1. 권장 구성

| | 권장 | 최소(토큰 절약) | 쓰지 말 것 |
|---|---|---|---|
| **세션 모델**(설계·집필·검수가 이 모델을 따른다) | Opus급 | Sonnet | Haiku |
| 조사 | Sonnet(기본값) | Sonnet | — |
| 한글 변환 | Sonnet(기본값) | Sonnet | Haiku |
| 검수 | 세션 모델 그대로 | 세션 모델 그대로 | 어떤 경우에도 낮추지 않음 |

- **좋은 결과를 원하면** 세션을 Opus급으로 연다. 집필 블라인드 채점에서 30점 중 27점으로 가장 높았고, 미확보 근거마다 `[보강 필요]`를 달았으며, 과제마다 우선순위 근거·반론·"이 조건이면 성립하지 않음"을 붙였다.
- **토큰을 아끼려면 Sonnet 세션까지가 하한이다.** 집필 25점으로 근거에 없는 내용을 지어낸 곳이 없었다. 다만 확인 안 된 사실 하나를 "확인된다"로 과하게 확정했고, 과제가 '확인·공개' 위주라 회의 안건으로서의 밀도가 Opus보다 낮았다. 검수가 그런 곳을 잡아 주므로 실무에 쓸 수 있는 수준이다.
- **Haiku는 어느 단계에도 권하지 않는다.**
  - 집필 16점: 근거 파일에 없는 부처 간 협의 과제 4건과 조문 구조를 `[보강 필요]` 없이 지어 넣었고, 시행령에 있는 불복 절차를 "규정 없음"이라 썼다. 평가자는 "다시 써야 한다"고 판정했다.
  - 한글 변환: 본문의 약 45%와 표 칸 내용을 잃은 파일을 만들고도 "무손실, 유사도 0.999 이상, 제출 가능"이라고 보고했다. 그래서 변환 기본값을 Haiku에서 Sonnet으로 올렸다.

## 2. 어디까지 되나 — 단계별 실측

| 단계 | 모델 | 결과 |
|---|---|---|
| 집필 | Opus | 블라인드 27/30. 근거 충실성 만점, 분량은 6쪽 상한 근처 |
| 집필 | Sonnet | 블라인드 25/30. 지어낸 것 없음, 과확정 1건, 간결 |
| 집필 | Haiku | 블라인드 16/30. 사실 오류 1건과 근거 없는 내용 다수, 표 칸 수가 머리글과 맞지 않아 렌더가 깨짐. 자기보고 글자 수 2,580자 ↔ 실측 6,812자 |
| 한글 변환 | Sonnet | **표 3개 모두 행·열 1:1 일치, 본문 왕복 유사도 1.0000**, 날짜 오파싱 0, 파일 생성까지 약 1~2분 |
| 한글 변환 | Haiku | 본문 유사도 0.70(원고 7,441자 → 4,046자), 원고에 없는 결재란 표 추가, 약 6분. 자기보고는 "무손실" |
| 조사 | Sonnet | 국내·해외 각 2~2.5분. 법령 원문을 열어 조문을 확인했으나, 분할당 도구 20회 상한에 걸려 운영 실태 보도를 놓침(§5) |
| 검수 | Opus | 5.5분, 웹·법령 원문 대조 약 20회로 [필수] 6건을 잡음 — 현행 조문 판 오류, EU 조문 대상 오기, 언론 인용 과장 등 |

"편집이 안 깨지는가"는 Sonnet 변환에서 **표·본문이 원고와 글자 단위로 일치했다**는 데까지 확인했다. 쪽 배치·줄바꿈은 kordoc 렌더러가 이 환경에서 작동하지 않아 화면으로 확인하지 못했다. 최종본은 한글에서 한 번 열어 보아야 한다.

**어느 모델이든 자기보고를 믿지 않는다.** 이번 시범에서 틀린 자기보고가 두 번 나왔다(Haiku 집필 글자 수, Haiku 변환 "무손실"). 킷은 리더가 점검기와 수치 대조를 직접 다시 돌리게 되어 있다.

## 3. 얼마나 걸리나

**브리프(4~6쪽) — 약 21분** (Opus 세션, 사람의 승인 대기 시간 제외)

| 단계 | 소요 |
|---|---:|
| 설계(의도 확인서·목차) | 3.5분 |
| 리더 점검 + 설계 게이트 ∥ 조사 2분할 | 약 7분 |
| 집필 | 2.5분 |
| 검수(원문 대조 포함) | 5.5분 |
| 검수 지적 반영(리더 직접) | 1분 |
| 한글 변환(Sonnet) | 약 2분 |

- 안내 예산 23분 안에 들어왔다. 실제로는 여기에 **사람의 확인 두 번**(분기 질문 답, 목차 승인)이 더해진다.
- **표준 보고서(50쪽 이상)는 이번에 다시 재지 않았다.** 이전 실측을 바탕으로 한 안내 예산은 약 52분(설계 8·조사 12·집필 15·검수 12·변환 5)이고, 조사·집필·검수를 나눠 동시에 돌린다는 전제다.
- **같은 요청을 일반 Claude Code에 주면 약 6분**이 걸렸다. 킷은 약 3.6배 느리다.

**토큰** — 킷 기본 경로의 하위 에이전트 처리 토큰은 변환을 빼고 약 118만이었다(설계 20만·게이트 17만·조사 38만·집필 20만·검수 23만). 일반 Claude Code는 약 21만으로, 킷이 약 5.7배다. 단계마다 역할 파일과 근거 파일을 새로 읽기 때문이다. 처리 토큰에는 캐시로 읽은 양이 섞여 있어 비용과 정비례하지는 않는다.

## 4. 일반 Claude Code와 비교하면

같은 요청을 같은 모델(Opus)에 스킬 없이 준 판과 킷 최종본을, 어느 쪽인지 가린 채 감사자가 원문을 직접 열어 대조했다.

| | 일반 Claude Code | 이 킷 |
|---|---|---|
| 사실 오류(❌) | 1건 | 0건 |
| 과장·단정(⚠️) | 3건 | 2건 |
| 확인하지 못한 것의 처리 | 본문은 단정, 끝에 한계 절 | 문장·표마다 확인 상태, 과제마다 성립 조건 |
| 회의 안건으로서의 쓸모 | **4/5** | 3/5 |
| 한 번 읽고 잡히는가 | **4/5** | 3/5 |
| 분량(요청 4~6쪽) | 약 2.5배 | 요청 범위 |
| 소요 시간 / 토큰 | **약 6분 / 약 21만** | 약 21분 / 약 118만 |
| 남는 것 | 결과 파일 하나 | 설계·게이트 판정·근거 장부·초안·검수 지적·한글 파일 |
| 감사자 선택 | **회의에 낼 판(고친 뒤)** | — |

**이번 시범에서는 킷이 졌다.** 이유가 분명하다.

1. **조사가 핵심 질문에서 굶었다.** 요청의 핵심이 "실제로 어떻게 돌아가고 있는지"였는데, 킷 조사관이 도구 20회 상한에 걸려 지원데스크 상담 건수, 확인 요청 건수, 기관의 자체 판정 사례 보도를 찾지 못했다. 일반 Claude Code는 도구를 47회 써서 이것들을 찾았고, 감사에서 수치가 원문과 맞았다.
2. **"찾지 못했다"가 요약에서 "없다"가 됐다.** 본문은 "공개 자료에서 확인되지 않음"이라 유보했는데 요약은 "공개된 것이 없음"으로 줄여, 진단 자체가 틀린 것으로 판정됐다.
3. **확인 상태 표시가 요지를 가렸다.** 문장마다 "(해설·보도 기준)"을 달자 읽기가 무거워졌다.

이 세 가지는 시범 직후 킷에 반영했다 — 핵심 항목이 상한에 걸리면 리더가 그 항목만 표적 보강 조사를 한 번 더 돌리고, 요약이 본문보다 세게 말하지 못하게 하고, 확인 상태는 출처 줄·각주·한계 절로 모은다. **고친 뒤의 성능은 아직 다시 재지 않았다.**

**킷이 앞선 것**은 이전 비교 실험([vanilla-vs-kit.md](vanilla-vs-kit.md))과 같은 방향이다. 사실 오류가 적고, 확인하지 못한 것을 확인한 것처럼 쓰지 않으며, 요청 분량을 지키고, 작업 과정이 파일로 남아 몇 달 뒤 "이 숫자 어디서 나왔나"에 답할 수 있다. 일반 Claude Code가 앞선 것은 속도·토큰, 그리고 조사를 넓게 해서 얻는 현황의 풍부함이다.

**어느 쪽을 쓸까**
- 회의 전날 현황을 넓게 훑을 초안이 필요하고 사람이 사실을 다시 확인할 수 있으면 → 일반 Claude Code가 빠르다.
- 밖으로 나가는 문서, 숫자 하나가 틀리면 곤란한 문서, 나중에 근거를 대야 하는 문서 → 킷.

## 5. 측정 조건과 한계

- 세션 모델 Opus 5.5. `sonnet`·`haiku`는 Claude Code 에이전트 모델 별칭(Haiku는 Haiku 4.5).
- 사람의 확인(분기 질문 답, 목차 승인)은 리더가 기본 가정으로 대신했고 대기 시간은 뺐다.
- 변환·감사 단계에서 인프라 장애(에이전트 3개가 동시에 10분 무응답)가 한 번 있었다. 손실 시간은 소요 시간에서 뺐다.
- 채점자·감사자도 Opus 한 명씩이다. 판정자가 같은 계열이라 놓치는 것이 있을 수 있다.
- 이번 시범에는 집필 문체 메모(`policy-report-style.md`)가 들어가기 전의 킷을 썼다.
