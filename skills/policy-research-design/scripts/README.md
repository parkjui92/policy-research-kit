# 의도 파악의 검증 도구

설계 단계가 사용자의 요청을 맞게 읽었는지를 판정하는 도구 셋. 표준 라이브러리만 쓴다. 절차는 [../references/intent-analysis.md](../references/intent-analysis.md).

의도 확인서(설계 문서 §1)는 의도를 읽고 전달하는 쪽이다. 이 도구들은 그 읽기를 **판정하는 쪽**이다. 의도를 잘 전해도 결과를 판정할 수단이 없으면 위임이 성립하지 않는다.

| 스크립트 | 하는 일 | 누가 언제 |
|---|---|---|
| `check_intent.py` | 의도 확인서를 요청 원문 원장과 **글자로** 대조 | 설계자가 저장 직후(자기 점검), 리더가 게이트 직전(재실행) |
| `misreads.py` | 사용자가 바로잡은 읽기를 한 건씩 쌓음 | 리더가 방향이 뒤집혔을 때·분기 질문의 답이 기본 가정과 달랐을 때·초안에 "이게 아닌데"가 나왔을 때 |
| `regress.py` | 같은 요청들로 설계자를 다시 돌려 채점 | 설계 스킬·설계자 정의를 고쳤을 때 |

## check_intent.py

```bash
python3 scripts/check_intent.py \
  --request _workspace/00_request.md --design _workspace/01_research_design.md
```

- 원장 옆의 `_decisions.md`와 `00_input/`의 글 자료(md·txt)는 자동으로 함께 본다. 다른 원문은 `--source`로 준다.
- 브리프 경량판은 `--brief`(분기 질문 2개·수용 기준 2~3개 기준).
- 종료 코드 0 = [필수] 없음, 2 = [필수] 있음.

| 등급 | 걸리는 것 |
|---|---|
| [필수] | 〔명시〕로 적은 인용이 원문에 없음 · 리더 메모(④)에만 있는 말을 〔명시〕나 요구어로 올림 · 반영 위치가 빈 요구어 · 요구어 대조표 없음 · 옮겨 적은 요청 원문이 원장과 다름 · 기본 가정 없는 분기 질문 · 수용 기준 없음 · 의도 한 문장·확신도 없음 |
| [권고] | 요구어로 뽑히지 않은 원문 구간 · 〔명시〕인데 인용 없음 · 〔추론〕인데 단서 없음 · 등급 이름 표류 · 분기 질문 상한 초과 · 판정하기 어려운 수용 기준 · 핵심 요소가 미상인데 확신도 높음 · 접수 일자 없음 |
| [참고] | 〔미상〕인데 내용 칸이 채워짐 · 한 질문에 물음 여럿 · 따옴표 없는 요구어 행 |

**통과는 글자가 맞다는 뜻이지 해석이 맞다는 뜻이 아니다.** 과잉 해석, 무게중심, 질문이 정말 목차를 가르는가는 검토관이 본다.

**읽지 못한 것을 없다고 말하지 않는다.** `00_input`에 hwpx·pdf 같은 글로 읽지 못하는 첨부가 있으면 "원문에 없는 인용"을 [필수]가 아니라 [권고]로 낮추고 읽지 못한 건수를 알린다. 그 줄은 사람이 첨부와 맞춰 본다.

스크립트가 틀렸다고 판단되면 게이트를 끄지 말고 그 줄을 `_run_log.md`에 적는다. 오탐이 반복되면 스크립트를 고치고 `--selftest`에 사례를 더한다.

설계 문서가 지켜야 하는 형식(스크립트가 읽는 곳): 요구어 대조표 머리에 '요구어'와 '반영 위치' · 요소 표 머리에 '등급' · 분기 질문은 `Q1.` · 수용 기준은 '수용 기준' 제목 아래 `A1.`.

## misreads.py

```bash
python3 scripts/misreads.py add --harness policy --type 분량 --task "과제명" \
  --request "요청 원문의 해당 구절" --read "설계자가 어떻게 읽었는가" \
  --fix "사용자가 바로잡은 말(원문)" --rule "다음에 적용할 것(조건 → 읽는 법)"
python3 scripts/misreads.py summary
python3 scripts/misreads.py list --type 분량
```

- 파일: `~/.claude/intent-misreads.md` (환경변수 `INTENT_MISREADS`로 바꿀 수 있다). 추가 전용.
- 설계자는 요청 원문을 읽은 직후 이 파일을 읽고, 같은 유형의 단서가 있으면 〔추론〕의 **단서**로만 쓴다. 〔명시〕로 올리지 않는다.
- 같은 유형이 두 번 쌓이면 `summary`가 **승격 후보**로 표시한다. 그때는 사례 파일에 두지 말고 설계 스킬 본문의 규칙으로 올린다 — 같은 지적이 두 번 나오면 사람 기억이 아니라 작업환경에 박는다.
- 지난 일을 뒤늦게 적을 때는 `--date YYYY-MM-DD`.

## regress.py

```bash
python3 scripts/regress.py list
python3 scripts/regress.py prepare --out <실행 폴더> [--harness policy] [--cases a,b]
# → 리더가 <실행 폴더>/spawn_prompts.md 의 프롬프트로 사례마다 범용 에이전트를 띄운다(병렬 가능, model 미지정)
python3 scripts/regress.py score <실행 폴더> --record
```

- 사례: `../regression/cases/<id>/` — `00_request.md`(요청 원장), `00_input/`(첨부, 있으면), `case.json`.
- `case.json`의 `expect`는 기계가 채점한다(정규식 `any`·`all`·`none`, `where`로 구역 한정). `judge`는 채점표에 찍혀 사람이 본다. `truth`는 그 요청 뒤에 사용자가 실제로 한 말(정답지)이다.
- 회귀 실행의 에이전트는 오독 사례 파일을 읽지 않는다 — 사례의 답이 거기 적혀 있을 수 있다.
- `--record`는 `../regression/history.md`에 날짜·정의 파일 해시·통과 수를 한 줄 남긴다. 스킬을 고치기 전후를 견줄 때 쓴다.
- `prepare --defs-root <폴더>`로 다른 위치의 정의(agents/ 와 skills/ 를 품은 폴더)를 시험할 수 있다. 정의에 `paper`·`proposal` 설계자가 있으면 그 사례도 돌릴 수 있다.

### 사례를 늘리는 법

1. 실제로 받은 요청을 쓴다. **사용자가 방향을 바로잡은 요청**이 가장 좋다 — 그 뒤의 발언이 정답지다.
2. 요청문은 글자 그대로 `00_request.md` ①에 넣고 접수 일자를 적는다.
3. `expect`에는 정답지에서 나온 것만 넣는다("형태·분량을 분기 질문으로 묻는가"). 설계자가 낼 문장을 미리 정해 두고 그 문구를 찾지 않는다.
4. 제3자의 실명·연락처가 든 요청은 넣지 않거나 가명으로 바꾼다.
5. 실제 사례는 `real-`로 시작하는 이름으로 둔다 — `.gitignore`가 저장소에 들어가지 않게 막는다. 이 저장소에 든 것은 합성 사례뿐이다.

오독 사례가 새로 쌓이면 회귀 사례로도 옮긴다.

## 한계

- 글자 대조는 형식과 인용만 본다. 그럴듯하지만 틀린 해석은 통과한다.
- `expect`의 정규식은 낱말이 **있는지**만 본다. 맞는 맥락에서 쓰였는지는 `judge` 항목으로 사람이 본다.
- 회귀 한 번에 사례당 설계자 1회(약 5~6분, 병렬 가능)가 든다. 상시 돌리는 것이 아니라 스킬을 고칠 때 돌린다.
- 경로는 스킬 폴더(`skills/policy-research-design/`) 기준이다.
